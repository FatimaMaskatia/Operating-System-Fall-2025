Q1: Looking at the backtrace output, which function called syscall?
Ans: syscall() is called by the function usertrap() in kernel/trap.c at line 68

Q2:What is the value of p->trapframe->a7 and what does that value represent? (Hint: look at user/init.c, the first user program xv6 starts, and its compiled assembly user/init.asm.)
Ans: The value of p->trapframe->a7 is 0xf (15 in decimal).
#define SYS_open   15, this corresponds to the system call number SYS_open, meaning the user program is requesting the open system call (used in user/init.c to open files like /console).

Q3: What was the previous mode that the CPU was in?
Ans:The SPP bit is bit 8 of sstatus. if SPP = 0 → Previous mode = User (U-mode) and if SPP = 1 → Previous mode = Supervisor (S-mode)
The value of sstatus shows that the CPU was previously in user mode (U-mode) before switching to supervisor mode (S-mode) to handle the syscall.

Q4: Write down the assembly instruction the kernel is panicing at. Which register corresponds to the variable num?
Ans: Command: grep 80001cf8 kernel/kernel.asm
Output: 80001cf8:   00002683                lw      a3,0(zero) # 0 <_entry-0x80000000>
Assembly code: lw a3,0(zero)
The variable num corresponds to register a3

Q5:Why does the kernel crash? Hint: look at figure 3-3 in the text; is address 0 mapped in the kernel address space? Is that confirmed by the value in scause above? (See description of scause in RISC-V privileged instructions)
Ans: The kernel crashes because it executes lw a3,0(zero) at 0x80001cf8, which attempts to load from address 0x0. Address 0x0 is not mapped in the kernel address space, so
the hardware raises a page fault trap. The scause value, that is 13 (load page fault) confirms it was a page fault as kernel tried to read from 0x0. This is why the kernel panics.

Q6: What is the name of the process that was running when the kernel paniced? What is its process id (pid)?
Ans: The process that was running when the kernel panicked is init, and its pid is 1.
